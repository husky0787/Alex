實作進度見 [alex-v1.md](alex-v1.md)：任務 1–3 已合併，後續分析接入與雲端／Kubernetes 驗收尚待完成。下列 Problem Statement 描述規劃起點；Implementation Decisions 描述第一版目標。現階段隔離紀錄以資料庫原因與原始物件關聯實作，S3 不同 prefix 的配置仍待後續雲端工作驗證。

## Problem Statement

使用者已有包含個人修正的 Alex 課程專案，但目前缺乏可追溯的日行情歷史、可恢復的擷取流程，以及經驗證的 Kubernetes 部署。現有行情失敗路徑會產生隨機價格，雲端完整研究鏈是否可用亦需重新驗證。使用者需要在一個月內做出可展示、可重現且能清楚解釋個人貢獻的作品。

## Solution

在既有平台加入固定 20 支美股／ETF 的日行情流程、最近 90 個曆日內交易日回補、資料品質與恢復能力，讓畫面及分析使用已驗證價格。API 和 ETL 先在本機 Kubernetes 驗證，再於短期 EKS 環境完成 AWS 整合、告警及回滾驗收；既有分析 agents 保留 Lambda。恢復並驗證文字研究與檢索鏈，最後提供完整操作及展示證據。

## User Stories

1. 作為使用者，我希望看見支援的 20 支標的，以便知道資料涵蓋範圍。
2. 作為使用者，我希望看到行情的交易日期和來源，以便判斷資料是否適合使用。
3. 作為使用者，我希望查看最近 90 天內的歷史行情，以便理解變化。
4. 作為使用者，我希望過期與缺漏資料有明確標示，以免誤認為即時價格。
5. 作為使用者，我希望分析只採用可追溯價格，以便理解報告的依據。
6. 作為使用者，我希望缺少必要價格時得到具體原因，以便補齊持倉資料。
7. 作為使用者，我希望報告保留當時價格依據，以便之後重新檢視。
8. 作為使用者，我希望研究引用可辨識來源與時間，以便理解檢索內容。
9. 作為使用者，我希望研究服務失敗時報告明確揭露限制，以免誤信不存在的研究結果。
10. 作為使用者，我希望帳戶和投資組合僅限本人存取，以保護資料。
11. 作為操作者，我希望每日自動取得行情，以免人工反覆更新。
12. 作為操作者，我希望保存原始回應，以便追查資料轉換問題。
13. 作為操作者，我希望不合格資料被隔離並附原因，以便修正而不污染有效資料。
14. 作為操作者，我希望暫時故障可重試且有停止條件，以免任務無限重跑。
15. 作為操作者，我希望重跑及並行執行不產生重複行情，以保持資料正確。
16. 作為操作者，我希望缺漏日期可回補，以便故障後恢復。
17. 作為操作者，我希望看到每次執行的狀態、筆數、耗時和失敗原因，以便診斷。
18. 作為操作者，我希望供應商修訂可追溯，以便辨認數值變更。
19. 作為操作者，我希望工作負載使用各自最小權限，以限制不必要的存取。
20. 作為操作者，我希望 Pod 故障可恢復、異常可通知，以便維持服務。
21. 作為操作者，我希望版本更新失敗可回滾，以便恢復可用版本。
22. 作為專案擁有者，我希望能重建及清理展示環境，以控制 credit 使用。
23. 作為面試者，我希望有實測紀錄與操作說明，以便清楚展示個人貢獻。

## Implementation Decisions

### 已確認的限制

- 固定 20 支美股／ETF；每日 OHLCV；最近 90 個曆日內的交易日回補。
- 使用者表示剩餘 AWS credit 約 US$100；有效期限、適用服務與即時剩餘額尚待核對。
- 目標 2026-11-25 前完成，可提前；每週投入時間未指定。
- 使用個人儲存庫 husky0787/Alex。目標是可驗證的資料工程及 Kubernetes 個人專案。

### 已確認的實作方向

- 沿用現有行情供應商整合方向，先驗證帳號日資料與歷史範圍權限；實作前固定標的清單、調整價格口徑與交易日曆。免費方案不符合時回報差距，不默認購買付費資料。
- 將擷取、原始回應保存、清洗、品質驗證、載入與執行紀錄封裝為一個 pipeline 入口；每日與回補傳入不同日期參數，共用行為。
- S3 使用獨立於前端的私有資料 bucket；原始資料與隔離資料以不同 prefix 保存。prefix 是邏輯分類，存取隔離由 IAM/bucket policy 實際約束。
- 新增日行情與執行紀錄模型。觀測值以供應商、標的、交易日、調整口徑識別；保存來源、擷取時間與資料版本。
- 檢查必填欄位、型別、日期、有限正數價格、OHLC 關係及非負有限小數成交量。2026-10-25 真實來源驗證確認 Massive 已提供小數股成交量，因此修正原先「整數」假設並保留來源精度。隔離不合格列；部分失敗不偽裝成全量成功。
- 原始物件保存、資料庫交易與完成進度明確分階段。S3 與 PostgreSQL 不假設跨服務原子性；重試以內容識別和執行紀錄恢復，完成進度不越過未處理缺口。
- 行情過期依最新應已發布交易日判斷，不把週末或尚未發布的資料當缺漏。顯示最新可信價格及 stale 狀態；沒有可信價格則 unavailable。
- 分析開始時固定引用的行情版本；任何必要持倉沒有可信價格或超出支援清單時，回傳明確錯誤，不產生不完整的整體估值。過期價格可使用，但畫面及報告須標明日期與警示。
- 未有新管線來源的既有 current_price 不能默認為可信；移除隨機價格 fallback。
- 文字研究保留來源 URL、擷取時間、研究識別碼，經 embedding 和向量儲存後檢索。服務失敗明確揭露研究不可用。
- API 用 Kubernetes Deployment；日常 ETL 用 CronJob，回補用 Job。資料層冪等與鎖補足排程層防重疊。
- API／ETL 分別配置工作負載身分、秘密來源、健康檢查、資源限制；HPA 用於 API 並驗證 metrics 前提。AI agents 的 SQS／Lambda 結構先保留。
- 本機先驗證，再集中 2–3 天 EKS 驗收。US$80 規劃支出和 US$20 緩衝涵蓋既有 AWS 用量；不是完整報價或強制支出上限。部署前計入節點、ALB、網路、儲存、模型及其他服務，並驗證 credit。
- CI 使用固定映像 digest 與短期 AWS 身分；有費用的部署採受控觸發。切換入口保留回滾路徑；資料庫採向後相容遷移。
- 每次測試保存日期、commit、環境、結果、限制及費用。部署驗收不等於授權刪除既有含資料資源。

## Testing Decisions

### 已確認的兩個主要測試邊界

1. **資料流程入口到可查詢結果**：從標的及日期輸入 pipeline，檢查已保存原始資料、隔離原因、正式行情與執行紀錄。外部行情 HTTP 使用可控制回應，資料庫使用隔離 PostgreSQL 驗證約束及交易；本機物件儲存替代服務之後再以少量真實 S3/Aurora 案例驗證差異。
2. **已登入使用者到畫面／工作結果**：經現有 API 和分析工作介面檢查授權、價格日期、歷史、缺漏與過期狀態；付費模型與雲端依賴在一般測試中替代，受控雲端驗收才呼叫真實服務。

測試觀察外部結果，不綁定私有函式或內部呼叫次數（重試次數上限等契約除外）。沿用既有 Agent 本地／遠端驗證方式和 Tagger 重試測試的經驗，但檢查每個測試是否仍會存取 AWS，不把檔名當成本機隔離保證。

必要案例：正常日資料、429／timeout、schema 異常、壞 OHLC、週末休市、DST、缺一交易日、同日期重跑、並行回補、資料修訂、寫入中斷、過期價格、必要持倉缺價、研究不可用、跨使用者授權、Pod 故障、告警送達與失敗回滾。

真實端到端驗收須通過登入、持倉、每日行情及歷史、分析報告、研究檢索。UI/API 驗收以日期與來源呈現一致為準；維運驗收以實際事件、恢復及通知證據為準。

## Out of Scope

- 即時行情串流、全市場資料、下單交易或投資績效承諾。
- 第一版把所有 AI agents 遷移到 Kubernetes。
- 長期全天候 EKS 展示、多區域高可用及企業級 SLA。
- 默認購買付費行情、超出 credit 的額外現金支出。
- 以新增技術數量代替有效的端到端驗收。
